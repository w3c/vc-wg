Render Method

dmitriz: Quick update on the VC render method and discuss issue 1653.

w3c/vc-data-model#1653

dmitriz: This was opened on the VC data model as a result of a discussion in the render method task force.

dmitriz: VC render method task force has defined 3 main suites for rendering VCs for anything that will render VCs, a digital wallet, a website, whatever it is.

dmitriz: We don't want every renderer to have to reimplement or customize rendering.

dmitriz: To that end, we have a notion of a static render suite that is for an NFC payload, or a PDF, etc.

dmitriz: This quite is fairly basic.

dmitriz: The second suite is codenamed "Summary" and is likely to change. The TF still has to finalize the name. It's a set of field labels and other metadata that helps with displaying the VC more generically.

dmitriz: The third suite is a full one JS and HTML and CSS application that can be embedded in a sandboxed iframe.

dmitriz: You don't have to come up with your own view but just directly show what the issuer wants.

dmitriz: Those are the three that have been finalized for a while and that you can expect in CR. Names might change, ideas are the same.

dmitriz: One of the main features we want to address before CR is i18n and multilanguage VCs.

dmitriz: This is the case for VCs in general and why it touches on the core VC spec and it's especially relevant for displaying information in different languages.

dmitriz: So issue 1653 came out of the discussion from the last task force call. There are 3 levels of internationalization. One is value level, we have a VC that's a bag of claims, the values of the claims themselves can be translated.

dmitriz: We have that ability from the VC data model spec which comes from JSON-LD.

dmitriz: You can have a language map, you can have a default language for the whole VC, you can apply individual languages for different values, all inherited from JSON-LD.

dmitriz: It doesn't apply to the field labels though.

dmitriz: I honestly haven't seen too wide of an implementation for these and the European wallet uses something else -- but values are handled.

dmitriz: Level 2 is translating on a field label level. Picture a diploma -- that might have a field level for a title and description of a course.

dmitriz: In English and some other languages it's just "Computer Science 101"

dmitriz: The values here we get for free from JSON-LD.

dmitriz: The problem kicks in with a third level of localization.

dmitriz: That is that we need to able to translate not just the field labels, but the layout.

dmitriz: This medical certificate looks different depending on the local, the layout and colors, date time, might all change.

dmitriz: Even though it's the same RFC date string under the hood, the display must be different.

dmitriz: That's where the argument came in -- one of the proposals was to add an "inLanguage" property.

dmitriz: There's some current objection in the group for adding that.

dmitriz: The issue 1653, on the core data model was opened. What's that issue about? Hey can we use an HTTP mechanism the Accept-Language mechanism?

dmitriz: So we have this notion of external resources.

dmitriz: You can link and secure with digest multibase.

dmitriz: Some related resources such as the HTML app used to display a VC, is hosted externally.

dmitriz: When requesting that external resource, that display for the iframe, we can say "I would like it in the English language or the French language, etc." and let the language negotiation take care of it.

dmitriz: There's division on the group on whether that's an appropriate mechanism and I wanted to bring that up here with the main group.

dmitriz: The are considerations, implementation requirements, the server side aspect, whether it fits the use cases, especially those in Europe, Canada, other multilanguage locals.

w3c/vc-recognized-entities#138

manu: Carolynn actually covered the main topic of discussion at the beginning of the call so I'll jump to a PR that we're unsure about. This came in from a security review on the specification.

manu: That review said that in the RE spec you have organizations that recognized other organizations to do certain things like issue a DL. However, the algorithm doesn't say -- if there are multiple hops in the chain, like a Global Authority that delegates to a National Authority and then to a Regional Authority, etc. -- you don't have anything in the spec that scopes that delegation down.

manu: There's nothing to say that something at the end of the chain can't just issue something for another country or whatnot.

manu: There's this question around -- "what are you allowed to do" per the RE spec. And that kicked off a fairly in depth discussion about that spec. Some people's mental model about the RE spec is that it says what an organization can and cannot do.

manu: And that is a bad mental model for what that spec is about. It's not about that at all.

<JoeAndrieu> +1 for redressing that mental model mistake

manu: VCs are about model world data models, anyone can say anything about anything.

manu: You can say that you recognize that something someone issues, but you can't restrict them.

manu: What someone can do, a Recognized Entity Credential issuer can say they'd recognize certain VCs from a University, but they can't stop that University from issuing whatever they want.

manu: So we're figuring out the proper language to use to respond to the security review here to make it clear how to prevent certain types of scoping attacks, but that the technology is not capable of preventing orgs from issuing other types of credentials.

JoeAndrieu: +1 to everything you just said, I really appreciate the continuing efforts to shift away from the allowance language.

JoeAndrieu: When I talked with Simone about this -- the language currently is about chain of authority and applies the legitimacy of transitive trust and that's a problem. I could choose to trust both AAMVA or AAA for some VCs.

JoeAndrieu: That pattern -- "I'm only trusting the list maker" follows a coherent trust model, but if we're creating a certificate hierarchy then you have to independently evaluate what it implies.

JoeAndrieu: The DNS architecture for TLS in particular, started out with an ambition about what it meant to get a green lock on a URL -- that turned out to be more burdensome than it was worth than to just secure the endpoint.

JoeAndrieu: Let's Encrypt just makes sure you can secure the traffic but no longer checks you as a company, etc.

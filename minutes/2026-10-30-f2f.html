VCALM

kezike: Going to talk today about the VCALM spec and its path to CR.
… Before VCALM was a concept we had the foundational VCDM specification, which specifies what a valid VC looks like, what properties are acceptable, and that existed in a vacuum.
… We needed a way to be able to do something with this VC, both from the standpoint of the issuer as well as the holder and the verifier.
… So we essentially needed a mechanism to enable exchanging and delivery/presentation of credentials.
… Generally, we need to manage the lifecycle of a VC under the three party model
… It would be great if we could do this in a modular and extensible way without binding clients to vendor solutions.
… VCALM stands for VC API for Lifecycle Management - it's a set of HTTP apis for the different roles in the 3 party model.
… This helps the roles to manage the VCs that relate to them and exchange these VCs with other parties.
… It supports issuance, verification, presentation, and status management.
… It supports repeated actions in a single exchange - such as multiple credentials delivered to a holder.
… It also supports verification steps before issuance steps, as a feature that is worth calling out.
… We have a notion of an administrator who is responsible for configuring the different services that will be used by the other parties
… We are careful to not put too many restrictions on what admins can do or how they set up services.
… The important part is the output - this is a key part of the specification.
… The issuer is able to leverage an issuance service that the admin sets up, whether to do issuance, deliver a credential, or respond to an exchange request.
… The verifier is able to verify credentials that the holder presents.
… A coordinator is a component of a "role" that is responsible for business logic - preparing data that needs to go into a credential, for example.
… It acts on behalf of the different parties in the three party model.

phila: overview of GS1 structure - there is a GS1 root key. No individual has access to this - but there are two sets of three people, and you need a representative of each set to access the root key.
… This is similar to the presented VCALM notion of admin role.
… The people behind the "GS1" entity are individuals - which is an implementation choice, but it is an example of how this is implementable.
… It is also an example of the complexity you get when you put this into a real organization, with a notion of an "organizational signature".
